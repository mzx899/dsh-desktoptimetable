# 方案 · 课表卡片尺寸调节（1.3.0）

> 需求：在「设置 → 课表外观」里增加一项，可以调整课表卡片的大小。
> 本文只写方案与实施清单，不改代码。选定粒度后再动手。

---

## 1. 现状盘点（决定工作量的三件事）

| 项 | 数字 | 出处 |
|---|---|---|
| 卡片尺寸写死 | `968×782`，其余尺寸全由它派生 | `Sources/DesktopTimetable/UI/TimetableLayout.swift` |
| `TimetableLayout` 引用 | **80 处 / 8 个文件** | 窗口、命中、图钉、日期面板、快照、自检 |
| CSS 写死 px | **268 处**（`width: 968px`、`grid-template-rows: 38px repeat(10, 54px)`、字号…） | `Resources/Timetable.css` |
| 窗口尺寸 | 卡片 + 两侧各 90pt 投影留白 = `1148×962`（**比屏幕可见区还大**，靠卡片本身夹屏） | `DesktopWindow.swift` / `AppDelegate.buildDesktopWindow` |
| 坐标链路 | 原生点 → `webView` 坐标 → `elementFromPoint`（CSS px） | `AppDelegate.forwardClickToCard` / `WebCardRenderer.hitTestInWeb` |
| 设置层现状 | `AppearanceConfig`（5 项）+ 每项一行滑块 + 立即写盘 | `Model/AppearanceConfig.swift` / `SettingsWindowController` |

结论：**等比整体缩放**是唯一不破坏现有版式的做法；不要一上来做宽高独立。

## 2. 方案 A（推荐）：三档预设 + 整体等比缩放

### 2.1 数据层

- `AppearanceConfig` 增加 `cardScale: Double = 1.0`；
  - 写入 `config.json`（`dictionary` / `init(_:)` 各加一项，缺省 1.0 → 老配置自动兼容）；
  - 取值夹取：`[0.80, 1.30]`，再叠加「按当前屏幕算出来的上限」。
- 新增纯函数（可单测）：

```swift
enum CardScalePolicy {
    static let presets: [Double] = [0.85, 1.0, 1.15]      // 小 / 标准 / 大
    static func clamp(_ v: Double) -> Double              // 0.80...1.30
    static func maxScale(for visibleSize: CGSize) -> Double
    //   = min((visible.h - 边距) / 782, (visible.w - 边距) / 968, 1.30)
}
```

> 这台屏幕实测：卡片 `782 × 1.15 = 899 < 937` ✓；`× 1.20 = 938 > 937` ✗
> —— 所以**最大档必须按屏幕算**，不能写死 1.3。

### 2.2 原生布局参数化

- `TimetableLayout` 保持静态调用（80 处调用点不用改），内部：

```swift
enum TimetableLayout {
    private(set) static var scale: CGFloat = 1
    static func apply(scale: CGFloat) { self.scale = scale }
    static var cardWidth: CGFloat { 968 * scale }
    static var shadowMargin: CGFloat { 90 * scale }   // 投影跟着缩放，视觉比例不变
    ...
}
```

- 所有派生量（`cardHeight`、`dayColumnWidth`、`gridOrigin`、`periodRect`…）继续用 `cardWidth` 推导，自动跟随。
- **唯一入口**：`AppDelegate.applyCardScale(_:)` 里先 `TimetableLayout.apply(scale:)`，再重建/重排窗口。
- 线程约定：只在主线程设置（和现在所有布局访问一致），文档写清楚。

### 2.3 窗口与视图重排

改档时的动作（一次性、同步）：

1. `TimetableLayout.apply(scale:)`；
2. `window.setContentSize(TimetableLayout.windowSize)`；
3. `card` / `interaction` / `webView` 的 frame 重设为新的 `cardRect`；
4. `interaction.setPinTitle(...)` 重新摆图钉；
5. 重新夹回屏幕：复用 `TimetablePinState.clampOrigin`，按**卡片**（不是窗口）夹；
6. `refreshCard()` + `saveWindowState()`（把新 origin 写盘）。

> 备选：直接重建整窗（`buildDesktopWindow` 重跑）。实现更省事，但有一下白闪；
> 推荐先做「就地重排」，失败再退回重建。

### 2.4 网页层缩放

- B 模式（默认，WKWebView 直接上屏）：`webView.pageZoom = scale`（macOS 11+ 可用，项目最低 12）。
  - 校验点：webView frame 变为 `968 × scale` 后，`document.documentElement.clientWidth` 应仍为 **968**（CSS 视口不变），否则说明缩放语义用错了。
- A 模式（快照）：快照按 `cardRect` 尺寸渲染，`pageZoom` 同样生效；回归里对比 A/B 两模式在 85% / 115% 下的截图一致性。
- **风险最高的一环：坐标换算**。`forwardClickToCard` 把原生点转成 webView 点后直接给 `elementFromPoint`；
  若 `pageZoom ≠ 1`，CSS px 与 view 点不再 1:1，需要显式 `÷ scale`（或改成整页 `zoom`）。
  → 实施时**先做一个 1 小时的 spike**：`pageZoom=0.85` 下点表头能否命中；不行再换方案
  （CSS `body { zoom: scale }`，或 webView 不缩放而是给 layer 加 transform、命中时 `÷ scale`）。

### 2.5 设置面板

在「课表外观」卡片里加一行（和现有 `fadeInRow` 同一套写法）：

```
卡片大小      [小 · 85%  ▾]        说明：只影响桌面上的课表，不影响设置面板
```

- `NSPopUpButton` 三档（`小 85% / 标准 100% / 大 115%`），当前值来自 `config.cardScale`；
- 改变 → `update("cardScale", v)`（复用现有 `update(...)` 通道）→ `AppDelegate.applyCardScale`；
- 超出当前屏幕上限的档位**置灰 + 提示**（例如「这块屏幕放不下 115%」），不静默改值。

## 8. 实施后修正（2026-11-06 下午，实机反馈）

实际做完滑块后，用户反馈「比例不对、拖动不流畅」。下面这些是**方案里没预料到**的，
以后再动缩放请先读这一节。

### 8.1 `pageZoom` 只适合 ≥ 100%

WebKit 在 `pageZoom < 1` 时会执行「最小逻辑字号 9pt」：

| 档位 | `.wkdate`（CSS 9.5px） | 顶栏 `.top` | 卡片高 |
|---|---|---|---|
| 100% | 9.5px | 55 | 773 |
| 85% | **10.59px** | 57.2 | 774.4 |
| 70% | **12.86px** | 63.3 | **782.5** |

顶栏被撑高后整张卡片跟着变高，随后内容溢出 → 滚动条 → 再吃掉 24px 宽度，
比例彻底不是等比。`minimumFontSize = 0` / WebKit 默认值都**关不掉**它
（`minimumLogicalFontSize` 默认 9，没有公开 API）。

**结论：缩小档位不能再用 `pageZoom`**。现在分两档：

- `s ≥ 1`：`pageZoom = s`（文字清晰，版式几乎不变）；
- `s < 1`：`pageZoom = 1` + `body { transform: scale(s) }`
  （纯视觉缩放，版式/字号一个都不改；`getBoundingClientRect` 返回视觉坐标，
  原生/JS 各自用 `rectScale` / `__ttGeomScale` 换算回来）。

代价：放大档文字最清晰，缩小档由合成器缩放着色（降采样，肉眼无感）。

### 8.2 网页永远不能出滚动条

`body` 固定 1148px，而缩放后视口可能是 1147（pageZoom 取整）或 804（transform）。
WebKit 一有 1px 溢出就加滚动条：卡片右侧投影留白里露灰条 + 吃掉 24px 宽度。
`html, body { overflow: hidden }` 是必须的（覆盖层自己内部滚）。

### 8.3 缩放必须同步的「隐形」几何

| 对象 | 不缩放会怎样 |
|---|---|
| `LiveContainerView.passthroughRect` | 放大后卡片右/上边**点不动**；缩小后卡片外空白挡住桌面 |
| `glassView.frame` | 用建窗时的旧高度翻 y → 玻璃整体下移（1.15 档 144pt），上没玻璃、下多一块 |
| `glassView.cornerRadius` | 圆角与卡片对不上（缩小档玻璃角更大） |
| 图钉（尺寸 / 间距 / 图标点号） | 卡片 70% 时图钉比例明显变大 |

### 8.4 滑杆上限必须按屏幕算

固定 115% 在这块屏上只能到 111.5%：拖过 111.5% 后卡片不再变化，
设置面板却每帧把滑杆值写回 111.5% —— 滑杆和鼠标抢位置（「粘、拖不动」），
显示的百分比也和实际大小不一致。
现在 `slider.maxValue = min(115%, CardScalePolicy.currentMaxScale())`，
副标题跟着显示真实上限；拖动中不回写滑杆，只在松手时回填一次。

### 8.5 拖动路径只做几何

每帧只允许：窗口重排 + 网页缩放 + 玻璃/图钉/穿透区域更新。
状态推送（整份 JSON）、网页矩形复量（跨进程）、悬停重算、写盘 → **松手做一次**。
实测 30 帧（70% → 100%）同步耗时平均 1.46ms / 最大 5.28ms，卡片中心漂移 0.5pt。

### 8.6 仍然存在的固有差异

原生卡片高 782（公式）vs 网页 773（内容撑），差 9px；缩放后按比例放大。
毛玻璃层现在按**网页矩形**铺（视觉正确），A 模式的原生卡片仍是 782。
不影响命中（B 模式全程用网页坐标）。

## 9. 实施后修正（2026-11-07，第二轮实机反馈）

用户原话：「继续修复课表放大的问题，以及放大缩小之后不能够拖动到边缘的问题」。
两条都是**常驻画布改造的尾巴**，方案里没写：

### 9.1 松手必须把「拖动预览」收尾成 pageZoom

拖动帧为了和窗口同步，一律走 `body { transform: scale(s) }`（合成器放大位图）。
1.3.1 的实现里，**松手**（设置面板开着）只是把最终值又走了一遍拖动帧，
没有切回 `pageZoom`：

- ≥100% 档整张课表一直是位图放大 → 字糊，重启才恢复；
- `usesPageZoom` 是按 `viewScale` 判的（≥1 就 true），松手后
  `viewScale = 1.12`、`rectScale` 也变成 1.12，而页面实际是 transform
  （`getBoundingClientRect` 返回的已经是视觉坐标）→
  玻璃 / 中心 / 命中换算**多乘一个 1.12**。实测中心跳 65.7pt。

现在 `commitCardScale`（面板开着）→ `finishCardScaleInCanvas` →
`WebCardRenderer.applyScale(_:keepingCardCenter:)`：

- ≥100%：`pageZoom = s`，translate = `center/s − (574, 476.5)`；
- <100%：仍是 transform，translate = `center − (574, 476.5)×s`；
- `center` 是**当前可见卡片中心**（`TimetableLayout.cardRect` 的中心），
  不是画布中心 —— 面板开着时窗口不动，卡片可能被夹在画布一侧，
  按画布中心重摆就会「松手跳一下」。

### 9.2 缩放一变，`cardRectOverride` 必须重写

`TimetableLayout.cardRectOverride` 是「可见卡片矩形（窗口坐标系）」，
拖动夹屏 / 毛玻璃 / 图钉 / 设置锚点都读它。它是按**当时的窗口原点**算的：

- 拖动帧每帧写一次；
- 松手 / 一次性重排（`performCardScale`）会把窗口摆到别处，
  但 1.3.1 没有更新它 → 过期。

过期值的后果（实测）：卡片「离屏幕边还有 72~134pt 就拖不动」；
放大到 112% 时夹屏把卡片顶出屏幕（y = −53，底部整条看不见）。

现在两层保护：

1. `TimetableLayout.apply(scale:)` 一改缩放就 **作废** 覆盖值（结构性护栏）；
2. `performCardScale` / `finishCardScaleInCanvas` 重排后写入
   `968×773×scale` 的新矩形（`TimetableLayout.webCardSize`，与网页实测一致）。

⚠️ 读覆盖值的顺序有讲究：`finishCardScaleInCanvas` 必须**先读中心、再
`apply(scale:)`**（后者会清空覆盖值）。

### 9.3 位置写盘改成「卡片」口径

面板开着时卡片可能被夹在画布一侧，而窗口不跟着动。1.3.1 直接存窗口原点，
重启后按「卡片居中」还原 → 卡片平移 `override.min − centered.min`（最多一百多磅）。
现在 `saveWindowState` 换算成「卡片居中时窗口原点该在哪」，重启严丝合缝。

### 9.4 新增回归入口

| 自检 | 验什么 |
|---|---|
| `--verify-scale-drag-edge` | 70/85/100/112% × 四方向拖到屏幕边（贴边误差 ≤2pt、完整可见）+ 真实用户路径「面板放大 → 关面板 → 拖到边缘」 |
| `--verify-scale-panel` | 松手 `pageZoom` / 中心不跳 / 玻璃不跳 / 关面板不跳（新增断言） |
| `--shot-web-card <png> [scale]` | 网页层出图（`--shot-card-scale` 只有原生层） |

实测：112% 左上 `x=0.002`、上边 `948.99`（可见区 949）；
面板路径 112% 左上 `(-0.08, 83.12)`、右下 `(427.92, 53.12)`。

### 9.5 缩放锚点必须「每轮释放」+ 页面原点每轮重取

同一个 bug 族里的第三处（2026-11-07 追加）：

- `cardScaleAnchorCenter` 在拖动开始时锁一次，面板开着时松手**不清空** →
  「缩放一次 → 把课表拖走 → 再缩放」会按旧锚点摆，卡片被拽回老位置。
- `dragPageTopLeft` 只在 `enterDragWindow` 取；窗口在面板开着时被拖走，
  下一轮就按旧原点算 translate → 卡片多平移一次拖动距离（实测 +120pt）。
- `webCardCenterInWindow()` 一律返回窗口中心；卡片被夹在画布一侧时
  窗口中心 ≠ 卡片中心 → 锚点错（实测 62pt）。

约定：**面板松手清空锚点；新一轮缩放先 `dragWindowActive = false` 重取页面原点；
`webCardCenterInWindow()` 优先用 `cardRectOverride`。**
回归：`--verify-scale-panel` 的「缩放 → 拖走 → 再缩放」断言。

### 9.6 放到最大时卡片被画布裁掉（2026-11-07 第二轮）

用户截图：「放到最大，怎么右边被削了」。

- 旧实现「窗口固定 + translate 摆卡片」：面板开着时卡片被按屏幕夹回，
  于是偏到画布一侧；画布只比最大档卡片宽 `2×90×scale ≈ 208pt`，
  偏出一点就被 WKWebView 在边界裁掉（实测真实窗口右边被切 55pt）。
- 改成「窗口位置跟着卡片中心走（取整到整点）+ translate 补亚像素零头」：
  卡片永远在画布正中；缩放帧每帧最多移动窗口一次（只在夹屏/缩放边界变化时），
  抖动仍由 translate 补着。
- 口径变化：**窗口尺寸不变、位置跟随卡片中心**（不再是「位置全程不动」）。
- 回归：`--verify-scale-panel` 的「70% 贴左边 → 面板里放到最大」断言
  （卡片右 1194 < 画布 1296、网页右 1193.96 < 1296）。

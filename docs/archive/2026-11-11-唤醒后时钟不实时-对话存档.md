# 2026-11-11 · 唤醒后时钟 / 「正在上课」不实时 · 对话存档

> 本轮目标：修「刚打开显示屏时，卡片右上角的时间晚了 1 分钟、
> 也没显示『正在上课』」。
> 用户原话：
> - 「现在时间的显示和正在上的课的显示都不是实时状态，为什么不是没变的情况下 1 分钟更新一次」
> - 「就是我刚打开显示屏的时候正在上课但是课表上没有显示我正在上课而且时间晚了 1 分钟」
> - 运行的是「桌面上的」那份 app。

---

## 1. 先排除掉的：常态其实是好的

先按「常态下不实时」去查。为观察网页层到底有没有在走表，临时加了一个探针
（`DT_CLOCK_PROBE=1`，每 5 秒把网页里的时钟 / 状态条 / 定时器状态打进日志）。

| 场景 | 结果 |
|---|---|
| 空数据目录 | ✅ 时钟 16:41→16:42→16:43 自走；`timer=true` |
| 真实课表（周三 16:42 正在上「学术语言与研究方法（中级）」） | ✅ 时钟自走；「剩 58 分钟」→57→55→54→49→48 逐分钟递减 |
| 完整数据目录（含 `timetables/`） | ✅ 同样正常 |
| 别的 App 抢前台（TextEdit） | ✅ 照样在走 |
| WPS 铺满屏幕遮挡 | ✅ 照样在走；`hidden=false`、`vis=visible`、`bootErr=none` |
| `--verify-web-render` 的「时钟就地刷新」断言 | ✅ 本来就是绿的 |

网页里 `setInterval(updateLiveTexts, 10000)` 装着（`__ttClockTimer = true`），
`updateLiveTexts()` 每次都从 `new Date()` 现算 —— 逻辑本身没问题。

**结论：问题只出现在「刚打开显示屏」那一下。** 用户的补充描述才是关键。

---

## 2. 根因

**屏幕睡着时，WebKit 会挂起网页的定时器**（`setInterval` 不再触发），
原生这边的 `Timer` 也停。醒来后：

- 原生 10 秒定时器要等下一个档才恢复；
- 网页 10 秒定时器同样要等下一个档才恢复；

这中间卡片顶部显示的是**睡着前那一帧的旧值** —— 时钟落后一分钟、
状态条还停在「今天没有课」（没显示「正在上课」）。

而且**原来的唤醒处理根本没管卡片**：

```swift
// 原来只有这两句
self?.dayPanel?.handleDayChange()      // 日期覆盖层
self?.refreshReminderSchedule()         // 上课提醒排程
```

`refreshCard()` 一次都没调 —— 卡片没人负责叫醒。

### 2.1 漏掉的那条通知（关键）

原来只监听 `NSWorkspace.didWakeNotification`（**系统**睡眠）。
但笔记本合盖 / 手动关屏时，**系统不一定睡眠**，发的是
`NSWorkspace.screensDidWakeNotification`（**显示器**唤醒）——
只监听前者，这个场景**根本收不到通知**。

用户说的正是「刚打开**显示屏**」，所以必须监听这条。

---

## 3. 修

### 3.1 `AppDelegate.forceRefreshCard()`

绕过「按分钟才推一次」那道闸（`lastWebMinute`），强制推一次状态给网页 + 原生重画。

### 3.2 `WebCardRenderer.tickClockNow()`

主动叫醒网页自己的走表定时器（`window.__ttUpdateClock()`）——
顶部时钟 / 状态条是**网页**负责的，原生推状态**不会**重画那两处。

### 3.3 `AppDelegate.handleSystemWake()`

唤醒统一走这里：换日期 + 补排提醒 + **强制重画卡片**，
并在 **1.5 秒后补一刀**（网页的定时器可能还没真正恢复）。

### 3.4 两条通知都监听

```swift
wakeObserver = ... addObserver(forName: NSWorkspace.didWakeNotification, ...)          // 系统睡眠
screenWakeObserver = ... addObserver(forName: NSWorkspace.screensDidWakeNotification, ...)  // 显示器唤醒
```

两条都走 `handleSystemWake()`。

## 4. 自检

新增 `--verify-wake-refresh`：

1. 把网页里的时钟**改成 `00:00`**（模拟「睡着时冻住的旧值」）；
2. 走一遍唤醒路径（`delegate.testSimulateWake()`）；
3. 断言时钟**立刻**回到当前时间；
4. 再等 1.8 秒（验证「补一刀」），断言仍然正确；
5. 断言 `testWakeCount > 0`（唤醒路径确实被触发）。

已登记进 `AutomationMode.automationFlags`。

### 4.1 验证它**真的能抓到这个 bug**

临时把 `handleSystemWake` 里的 `forceRefreshCard()` 注释掉：

```
  唤醒前时钟：17:05
  唤醒后时钟：00:00　期望：17:05
❌ 唤醒后时钟没有回到当前时间：实际 00:00，期望 17:05
```

恢复修复后：

```
  唤醒前时钟：17:08
  唤醒后时钟：17:08　期望：17:08
✅ 唤醒后卡片顶部（时钟 / 状态条）立刻刷新：通过
```

## 7. 遗留 / 下一轮候选

- **`DT_CLOCK_PROBE=1` 保留**（排查「卡片顶部的时间不实时」时还用得上）。
- 真机**没有真正模拟过系统睡眠 / 屏幕关闭**（本会话不能安全地 `pmset` 睡眠）——
  修的是机制（唤醒通知 → 主动重画），自检走的是同一条 `handleSystemWake()` 路径；
  建议用户下次合盖 / 关屏后看一眼卡片顶部是不是立刻变成当前时间。
- 两个缩放问题仍未修（按约定要先做 spike）：
  100% 附近 pageZoom↔transform 突变；拖动缩放时羽化层闪烁。
- `--verify-panel-sections` 的 3 条既有失败（断言还停在 4 个板块 / 11 张卡片）可顺手修。

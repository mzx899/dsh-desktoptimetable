# 2026-11-09 对话存档 · 修「添加待办键盘进不去 / 取消要点两下」

## 用户原话

> 「现在输入日历点击了添加待办事项的时候输入框出现了但是这时候输入键盘无法聚焦，
> 而且第一次点击取消了之后再次打开添加待办事项取消要点击两次，应该还是聚焦的问题，查清楚」

## 本轮目标

查清并修掉两件事：

1. 点「＋ 添加待办」后输入框出现了，但**键盘进不去**（打不了字）；
2. 取消一次之后**再打开**输入框，「取消」要点**两下**才收得回去。

## 排查过程

### 第一步：读代码，找不到现成的解释

- `Resources/Timetable.js` 的 `ensureInput()` / `ensureTimePart()`：输入框元素**跨重绘复用**；
- `UI/DesktopWindow.swift` 的 `setTextInputMode` / `takeKeyForTextInput`：
  桌面窗口是 `.nonactivatingPanel`，靠「临时变 key + first responder 交给 webView」才能打字；
- `UI/WebCardRenderer.swift` 的 `forwardClick`：点击是**合成 JS 事件**转发的。

初判两个方向：① 原生侧拿不到 key；② 网页侧焦点掉了。**两边都要验。**

### 第二步：先写一个能复现的自检

关键约束（来自 README「真机焦点自检」一节）：
**从终端直接起的进程永远当不了 active app**（`NSApp.isActive` 恒为 false），
那样测出来的「打不上字」是**假断言**。所以自检必须经 **LaunchServices**（`open -n`）启动。

新建 `Sources/DesktopTimetable/main.swift` 里的 `--verify-todo-focus`：

- 走**和用户完全一样**的链路：真实鼠标事件 → `CardInteractionView` → `forwardClick`
  → 网页 DOM → `textInputFocus/Blur` → 原生拿 key + webView 拿 first responder；
- 报告写到 `DT_FOCUS_REPORT` 指向的文件（`make verify` 那种模式）。

**踩到的坑**（都记在代码注释里）：

- 自检块写在 `app.run()` **之前** → 异步步骤永远不执行 → 必须在自己块里补 `app.run()`；
- `focusVerificationMode` 走的是 `prepareForImportVerification()`，**不会**调 `showCard()` →
  窗口没 `orderFrontRegardless()` → 拿不到 key → 自检报**假 bug** →
  加了 `AppDelegate.testShowCard()`；
- 不预激活 app 时 `NSApp.isActive` 恒为 false → 必须在自检里显式激活并等它生效。

### 第三步：复现成功，两条根因各自浮出水面

**根因一（原生）—— app 停在「active 但没有 key window」。**

在 `takeKeyForTextInput` 里加诊断日志（`DT_DEBUG_INPUT=1` 时写统一日志）：

```
[TT-KEY] attempt=0 mode=true token=1/1 appActive=false isKey=false   ← 第一次打开
[TT-KEY] attempt=1 mode=true token=1/1 appActive=true  isKey=true    ← 激活过程给了 key ✅
[TT-KEY] attempt=0 mode=true token=3/3 appActive=true  isKey=false   ← 第二次打开
[TT-KEY] attempt=1..8 … isKey=false                                 ← 12 次重试全废 ❌
```

**AppKit 的规矩：`.nonactivatingPanel` 窗口只有跟着 app 的「激活过程」才能拿到 key。**

- 第一次打开时 app 还是 inactive → `NSApp.activate` 触发激活过程 → `makeKey()` 成功；
- 退出输入模式时 `DesktopWindow.setTextInputMode(false)` 调 `resignKey()` →
  app 变成「**active 但没有 key window**」（accessory app 退出输入模式不会 deactivate）；
- 于是第二次 `makeKey()` 被 AppKit **直接拒绝** → webView 拿不到 first responder
  → **键盘进不去**；
- 而且那 4 秒的重试每次都 `NSApp.activate` + `activateAllWindows` + `makeKey`，
  窗口被反复摆到前面 → **用户的点击被吃掉** →「取消要点两下」。

**根因二（网页）—— 共享的 input 元素每次重绘都被搬走。**

`dpTodoSection` 每次都 `h('div', { class: 'dpaddform' }, input)` 拼一个新表单 ——
`h()` 会把 `input`（**跨重绘复用的那个元素**）从旧表单里**摘走**挂到新表单上：

- 元素在 DOM 里被「摘下来再挂回去」→ **失焦** → `onblur` → `post('textInputBlur')`
  → 原生退出文本输入模式 → **键盘断掉**；
- 原生一退出输入模式就要重新抢 key（重试 4 秒）→ 又是「点击被吃掉」。

两条合起来，正好对上用户报的两个现象。

### 第四步：试过但**没用**的方案（别再试）

- **摘掉 `.nonactivatingPanel`**（临时改 styleMask）：窗口确实变成普通面板了
  （`styleMask=0`、`canBecomeKey=true`），但 `makeKey()` **照样被拒**。
  → 证明根因不是 styleMask，而是「不在激活过程里」。
  最终**没采用**这个方案（改 styleMask 有闪烁 / 丢 key 状态的风险，而收益为零）。
- **`NSApp.hide(nil)` → `NSApp.activate` → `makeKey()`**：能成（它制造了一次激活过程），
  但会把课表整个藏一下，用户能看见闪一下 → 不用。
- **`makeKeyAndOrderFront` + `orderFrontRegardless`**：还是 `isKey=false`。

## 最终修复

**原生（`Sources/DesktopTimetable/UI/DesktopWindow.swift`）**

- `setTextInputMode(false)`：窗口**是 key 的时候不交出 key**，只把 first responder 收回来
  （`if !isKeyWindow { resignKey() }`）。app 一直有 key window，
  下一次 `makeKey()` 照样认 —— 实测第二次打开 `attempt=0` 就 `isKey=true`。
- 诊断日志改成**只在 `DT_DEBUG_INPUT=1` 时**写。

**网页（`Resources/Timetable.js`）**

- `ensureAddForm()`：「添加待办」的表单 DOM **建一次就留着**，重绘时只更新值；
- `updateAddCard()`：「添加待办」那张卡也是**稳定节点**，同时装**两种形态**
  （收起态 `.dpadd` / 展开态 `.dpaddform`），来回切换只改 `display`；
- `syncCards()`：`add` 这张卡现在可以正常复用了；
- `window.ttAddFormVisible()`：**判「添加态开着没有」要看可见性**。

**自检侧的连带修正**：`--verify-day-panel` / `--verify-day-panel-click` 里几处
`!!document.querySelector('.dpaddform')` 改成 `window.ttAddFormVisible()`。

## 1. 1.2.4 · 「开 app 课表不出来 / 指针在课表上也不浮起来」

### 根因（有真机实测数据）

课表窗口层级 `-1`（普通窗口之下、桌面之上），而
`NSWindow.windowNumber(at:belowWindowWithWindowNumber:)` 在这个后台 App 里返回三种情况：

| 情形 | alpha | 它报回来的是 | 层级 | 旧判定 |
|---|---|---|---|---|
| 刚启动还没亮（`minOpacity = 0`） | 0.00 | 访达**桌面图标窗口** 34451 | `-2147483603` | 遮挡 ❌ 死锁 |
| 亮着，指针下面是课表 | 1.00 | **我们自己的窗口** | `-1` | 不遮挡 ✅ |
| 亮着，指针压着别的 App | 0.22 | **那个 App 的窗口**（如 DSH 297） | `0` | 遮挡 ✅ |

旧写法「不是我们的窗口 = 被盖住」把第一种也算成遮挡 → 课表永远停在
`minOpacity`（用户设 0 = 完全透明）→ 用户看到「没出来」。

### 修复

- 新增 `Model/HoverCoverPolicy.swift`：**只有层级比课表高**才算遮挡；
  同层不算；查不到层级时也不当作遮挡。
- 课表层级收成唯一一份 `HoverCoverPolicy.cardWindowLevel`（`-1`），
  `DesktopWindow` 与 `AppDelegate` 共用。
- 启动时「先亮一下」（0.35s 渐到 1，0.9s 后落回常态）+ 每 10 秒重算一次 hover。
- 删 `[TT-ALPHA]`，换成按需开启的 `DT_HOVER_DIAG=1`（打印指针/窗口号/层级/遮挡/inside/alpha）。
- 新增 `--verify-hover`，并登记进 `AutomationMode.automationFlags`
  （不登记的话自检会去动真实通知中心 —— 这条断言当场抓到过）。

## 2. 1.2.5 · 「点权限弹框的时候课表会淡掉」

- 授权框是**系统进程**的窗口（层级远高于课表、位置在屏幕中间），
  用户点「允许」时指针既离开卡片、那个点又被更高层窗口占着 → 必淡出。
- 新增 `Model/PermissionPromptWatch.swift`：弹框前 `begin("定位"/"日历"/"提醒事项"/"通知")`，
  拿到授权回调 `end(...)`；期间 `updateHover` 里短路 `inside = true`。
- 接入三处：`EventKitStore`（日历/提醒事项）、`WeatherProvider`（定位）、
  `ClassReminderScheduler`（通知）。
- 并行两框按原因分别记账；`onStateChanged` 接到 `updateHover(force:)` → 立刻生效不等鼠标。

## 3. 1.2.6 · 「输入待办时鼠标滑到别的列，正在输入的那列就没了」

- 覆盖层是**跟随指针**的：`DP.day !== day` 就 `openPanel(day)` 重建内容 → `<input>` 被销毁。
- 修复：`Resources/Timetable.js` 的 `onPointerMove` 在
  `DP.adding || DP.editingTodoKey` 时直接返回，不换列（点表头仍可主动换列）。
- `--verify-day-panel` 新增 `4c-13d-2`：编辑态/添加态下移动不换列、不丢输入；
  Esc 后恢复跟随（两边都验，防止把「跟随」整个关死也能通过）。

## 4. 1.2.7 · 「修改完成或取消之后，鼠标移到课表外面，课表没有消失」

### 定位

1. 先用 `DT_HOVER_DIAG=1` + 合成鼠标移动做**基线对照**：不经待办交互时，
   指针出卡片 `inside=0 hovering=0`，alpha 正常回落 → 主链路没坏。
2. 枚举能让课表强制亮着的短路：菜单标志（`defer` 配对）、3 秒菜单宽限期、
   `PermissionPromptWatch.isHolding()`（1.2.5 新加，上限 **120 秒**）、
   `topNumber == 自己的卡片窗口`。
3. 对上号：1.2.5 的保持依赖「回调一定来」，而 `DayPanelController` 注释早写过
   日历/提醒事项**并行**请求时「另一个请求一直挂着」—— 于是 `begin` 等不到 `end`。

### 修复

- `PermissionPromptWatch`：每笔 `begin` 各排一个 `DispatchWorkItem` **兜底超时**，
  默认 **10 秒**（原 120 秒），到点自动销掉并 `onStateChanged(false)` 立刻重算亮度。
- `DayPanelController.requestAccess` 的 10 秒收尾里加 `PermissionPromptWatch.endAll()`。
- `AppDelegate.updateHover`：`topNumber == 自己的卡片窗口` 不再直接算「在卡片上」，
  改走「卡片矩形 + 迟滞」；只有**本 App 的其它窗口**（设置面板/对话框）才整体算「在课表这边」。
- 迟滞 **14pt → 8pt**（用户被卡住的位置正好在卡片外 13.9pt）。
- 单元测试补：兜底超时真的销掉那一笔、超时后 `activeReasons` 清空且只通知一次退出。

## 5. 尺寸调节：只有方案，未实施

用户问「在课表外观里加一个调整课表大小的栏目，工程量是多少」。已写方案：
**`docs/方案-课表尺寸调节.md`**（仓库内）。

要点：

- 版式是像素级写死的：`TimetableLayout` 80 处引用 / CSS 268 处 px / 卡片 968×782 / 窗口 1148×962；
- 唯一不破坏版式的做法是**整体等比缩放**（`WKWebView.pageZoom`，macOS 11+ 可用）；
- 推荐先做**三档预设（85% / 100% / 115%）**，约 **9 小时**（难度 5/10）；
  连续滑块 +1~2 小时；拖角自由缩放 +1~1.5 天（要 CSS 变量化重做版式）；
- 最大档必须**按屏幕算**（这台 115% 刚好，120% 就超出可见高度 937）；
- 最大风险是 `pageZoom` 与 `elementFromPoint` 的坐标换算，方案里排了 1 小时 spike 先验。

## B. 定位到的 5 个根因（都有实测数据）

| # | 根因 | 实测 |
|---|---|---|
| 1 | 玻璃层 y 用了**建窗时**捕获的 `webHeight`（962） | 1.115 档玻璃下移 144pt：上半截没玻璃、下半截多一块 |
| 2 | `LiveContainerView.passthroughRect` 缩放后没更新 | 放大后卡片右/上边点不动；缩小后卡片外空白挡桌面 |
| 3 | `pageZoom < 1` 触发 WebKit **最小逻辑字号 9pt** | 0.7 档 `.wkdate` 9.5→12.86px、顶栏 55→63.3、卡片 773→782.5 |
| 4 | 卡片变高后溢出版式 → 滚动条 | 视口 1147 vs body 1148 → 出现滚动条，吃掉 24px 宽度、投影留白里露灰条 |
| 5 | 拖动每帧做重活 + 滑杆被回写 | 每帧推整份状态 / 跨进程量矩形 / 重算悬停 / 窗口摆两次；滑杆上限 115% 但屏幕只能到 111.5%，每帧 `setValue` 和鼠标抢 |

## F. 追加：放大缩小时的「轻微抖动」

用户追加问「放大缩小的时候，课表有轻微的抖动是正常的吗」。不是正常的，查出来是**锚点取错**：

- 锚点原来用原生 `TimetableLayout.cardRect` 的中心（整数取整），
  而用户看到的是网页卡片（严格按 scale 连续）。两者中心差随缩放变化，
  且每帧还重新读「当前中心」再取整 → 目标自己在跳。
- 实测 70% → 100% 拖动中，**网页卡片中心漂移 2.05pt**（肉眼可见的一两个像素抖动）。
- 修复：拖动开始时**锁一次**锚点，锚点用 `WebCardRenderer.cardCenterInWindow`
  （网页卡片中心，随 scale 连续）；窗口定位 / 量了再修都按它；松手释放。
- 结果：可见中心漂移 2.05pt → **0.74pt**（剩下的是窗口吸附半像素的 1 个物理像素）；
  拖动单帧仍 1.34ms。
- 复跑：`make test` 2018 通过；`--verify-card-scale` / `--verify-hover` /
  `--verify-day-panel` / `--verify-day-panel-click` / `--verify-pin-flow` /
  `--verify-settings-card` / `--verify-panel-sections` 全通过。

## G. 追加：快速拖动仍抖 + 系统板块版本号

- 用户反馈：「拖动比较快的时候，抖动还是很明显。另外在课表设置的系统里面，
  最下面加上当前的版本号」。
- **快速拖动抖动**：窗口尺寸/位置是主线程同步改的，网页缩放是跨进程异步的；
  先改窗口后改网页时可见卡片按 `574×Δscale` 跳（拖越快跳越大）。
  修复：拖动帧串行化 —— 先 `applyDragScale` 让网页应用缩放，回调里再对齐窗口；
  拖动值只保留最新一份；去掉 16ms 节流（120Hz 屏上原来被钉在 60fps）。
  拖动期间统一用 CSS transform，松手切回 pageZoom。
- **版本号**：设置 → 系统 最下面加「桌面课表 · 版本 x.y.z」，
  从 `Bundle.main` 的 Info.plist 读（不写死）。新增 `--shot-settings … system` 出图参数。
- 验证：真实拖动路径 30 帧平均 3.71ms / 最大 8.17ms（120Hz 预算 8.3ms），
  可见中心漂移 0.74pt；`make test` 2018 通过；verify 全套通过；
  系统页截图显示「桌面课表 · 版本 1.3.0」。

## H. 追加：99~100 / 100~101 连续拖动时「整个画面抖一下」

- 用户反馈：缩放调到 100% 附近连续拖动时，整个课表会抖一下。
- **根因**：窗口服务器会把 `setFrameOrigin` 的小数**截断到整点**
  （独立程序实测：300.37→300、301.5→301、302→302）。卡片中心要随
  scale 连续移动，而窗口每帧移动又被取整 → 中心 ±0.5~1pt 跳。
  实测 98→102% 时，100% 这一步中心跳了 1.00pt（邻居 Δ 都是 0）。
- **修复**：拖动期间改用**固定的大窗口**（最大档尺寸，进入拖动时一次摆好，
  全程不动），卡片位置由 `translate(...) scale(s)` 决定 —— translate 可以
  落在小数上。玻璃 / 图钉 / 穿透区域按 translate 后的矩形同步。
  第一次尝试的「窗口照动 + translate 补零头」不可行：预测不了服务器怎么取整。
- **验证**：98→102% 每一步中心 Δ 都是 0.00pt（含 100%）；
  30 帧拖动 2.64ms 平均 / 6.13ms 最大；`make test` 2018 通过；verify 全套通过。

## I. 追加：点下滑杆瞬间「整张卡/面板错位一下再弹回」

- 用户截图反馈：点击拖动滑杆的瞬间，卡片/面板错位一下，马上回原位。
- **根因**：上一版「进入拖动时把窗口放大到最大档」——点下滑杆的那一帧
  窗口先变大/移位，网页的 transform（translate/scale）还没应用，
  于是卡片按旧布局出现在新窗口的左下角附近，下一帧才被 transform 拉回锚点。
- **修复**：进入拖动时**不改变窗口尺寸/位置**，直接沿用当前窗口
  （当前窗口本来就按当前 scale 摆好了卡片，transform 的 translate 约为 0，
  零过渡）；只有拖到卡片快超出窗口时才放大一次（100% 附近不会触发）。
- **验证**：98→102% 中心 Δ 全 0.00pt；30 帧 2.54ms/5.94ms；`make test` 2018、
  verify 全套通过；构建重新归档并重启。

## J. 追加：82% 附近又错位一下（拖动窗口的过渡）

- 用户截图：82% 附近又突然错位一下。根因是上一版「沿用当前窗口」在卡片快
  超出窗口时（从低档位往上拖）会再放大一次，84% 附近正好触发。
- **最终做法**：进入拖动时把窗口**一次放大到最大档，但保持窗口左上角不动**。
  网页内容从左上角往下排，左上角不动 → 卡片在屏幕上一点不挪，
  多出来的透明区域落在右下；整个拖动期间窗口不再变化。
  transform 只用 `translate + scale` 把卡片中心钉在锚点。
- 验证：98→102% 中心 Δ 全 0.00pt；30 帧 2.84ms/8.89ms；`make test` 2018、
  verify 全套通过；构建重新归档并重启。


## K. 追加：放大到 110% 时卡片被屏幕切掉

- 用户截图：110% 时左边一列没了，问「是不是把显示窗口固定了」。
- 根因：① 缩放锚点只保证中心不动，卡片大到边缘就有一半在屏幕外；
  ② 拖动窗口只在卡片附近，卡片被夹回屏幕后可能跑到窗口边界外被裁。
- 修复：① 每档把卡片中心夹进屏幕可见区（网页卡片尺寸）；
  ② 拖动窗口换成「屏幕可见区 + 四周 200pt」的画布，webView 在窗口里偏移，
  页面原点不动 —— 卡片不动、也不会被窗口裁。窗口扩大是原生的，
  不经过 JS，所以没有过渡闪动。
- 验证：左上/右下贴边拖动放大到 110%：屏内=true、窗内=true；
  98→102% 中心 Δ 0.00pt；测试/verify 全通过。


## L. 追加：松手后卡片和设置面板错位

## M. 追加：每次松手都闪 + 面板跟着动

- 用户反馈：每次拖动松手都闪，甚至设置面板会跟着移动。
- 根因：松手要把拖动画布缩回正常窗口、网页 transform 从 translate+scale
  切回 scale；窗口同步、网页异步 → 中间一帧闪。面板重对齐本身也是位移。
- 修复：**设置面板开着时松手保留画布**（窗口/页面原点都不动，只更新网页 scale），
  面板不自动移动；**关闭面板时**再一次性恢复正常窗口（被面板收走遮住），
  以当前卡片中心为锚点避免跳位。画布阶段不写 window_state。
- 新增 `--verify-scale-panel`：面板开 → 画布 1912×1296 → 松手窗口/原点不变
  → 关闭恢复 1206×1011、卡片中心差 < 0.5pt。make test 2023 通过。


## N. 追加：移动滑块后课表「对不齐」（网页停在上一档）

- 用户截图：滑块/状态 93%，卡片仍是 100% 大小。量图：面板 580pt=810px
  （比例 1.397），卡片 1365px≈977pt≈968×1.0，而非 93% 的 900pt。
- 根因：拖动时每帧都要等上一帧 `evaluateJavaScript` 回调
  （`dragScaleInFlight`）。拖动开始的画布/webView 视口变化会让第一帧
  （当前档的空操作）回调被拖住/丢掉；之后所有滑块值只进 pending 不落地，
  卡片停在 100%；松手也被 `if !dragScaleInFlight` 挡住。
- 修复：0.12s 兜底定时器强制重发 pending；松手强制重发最终 scale
  （作废在途帧，不等回调）；记录 JS 错误。
- 验证：连续 40 步快速拖动 → 最终 transform scale(0.95)、卡片宽 919.6pt；
  松手窗口不变；关闭面板中心差 <0.5pt；make test 2023、verify 全通过。
